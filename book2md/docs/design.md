## 2. 核心架构：三层复用模型

```
┌─────────────────────────────────────────────────────┐
│ L2 书目覆盖层  overlays/<书名>/                       │
│   内容级精确串、表/图重建、该书特有误识                 │
│   变更频率：每本书一次     载体：Python 规则模块 + JSON │
├─────────────────────────────────────────────────────┤
│ L1 学科规则包  packs/<学科>/                          │
│   数学：花体字母→p/q、事件定义、\mathcal{D}→∅、       │
│        数集记号词典、\oint 符号专项                    │
│   化学（预研）：方程式配平检查、可逆⇌、气标↑↓、         │
│        条件上下标、官能团、实验装置图 alt               │
│   物理（预研）：矢量箭头、SI 单位制、希腊字母、          │
│        v-t 图/电路图 alt                              │
│   变更频率：每学科每学期   载体：Python 规则模块        │
├─────────────────────────────────────────────────────┤
│ L0 通用引擎  engine/                                 │
│   提取驱动（PdfExtractor 抽象；默认 MinerU 远程适配器）· OCR 错识分类学（S1–S9/S12–S15）  │
│   渲染验证栈（KaTeX 预编译 + texmath 语义复刻）         │
│   双版本单体 HTML · 质量门流水线 · 验收报告               │
│   变更频率：几乎不动       载体：Python 包              │
└─────────────────────────────────────────────────────┘
```

**层间接口契约（interface contract，关键设计）**：

1. 规则统一表示为 `(名称, 正则, 替换, 适用范围)` 四元组，与现有 BATCH 列表同构——
   L1/L2 规则可以直接搬进现有 `BATCH`/`TARGETED` 数据结构，**迁移零翻译成本**。
2. 探测器也是四元组变体 `(编号, 检测函数, 学科白名单)`，通用探测器进 L0，
   学科探测器进 L1，由科目配置组装。
3. 科目配置（`configs/<科目>.json`）声明：册名列表、TOC 章目正则、
   探测器组合、规则包引用、HTML 主题、**知识库变体特性开关（公式双表示 alt、
   页码映射表等，见 §1.1 postprocess.py 行）**。**换科目 = 换一个配置文件**。

## 3. 规则沉淀与晋升机制（rule promotion）：产品的核心机制

新书上架的完整回路（本次数学项目已经人工实践过，现在把它固化为流程）：

```
        ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
 ① 提取    PdfExtractor 跑新书 PDF（默认 MinerU 远程适配器）→ md + 图 + 公式        │
        │                                          │
 ② 质量扫描    引擎探测器矩阵 + 渲染验证栈全量跑          │
        │     → A/B/C 三档问题清单（带行号与上下文）   │
        │                                          │
 ③ 分档处置                                          │
        │   A 档（括号失衡/游离$$/裸LaTeX）→ 引擎自动修 │
        │   B 档（学科通病）        → L1 规则包批量修   │
        │   C 档（内容存疑）        → 对 PDF 复核裁定       │
        │                            （联网/目检/hex）  │
        │                                          │
 ④ 固化    复核裁定结果写入 L2 覆盖层规则                 │
        │     带出处注释（哪一版教材、哪条依据）        │
        │                                          │
 ⑤ 晋升    同一模式在第 2 本书复现 → 晋升至 L1 规则包 ─┘
          （防止覆盖层膨胀：单书特有的不进规则包）
        │
 ⑥ 验收    全部质量门通过 → 交付双版本 HTML + 质检报告
```

**两条防退化纪律（anti-regression disciplines）**（从本次项目的教训中提炼）：

- **备份干净重跑**：任何规则修改后，从 `final_backup_*` 全量重跑，
  禁止在成品上打补丁——否则规则间相互作用不可复现。
- **字符数核对**：每轮修复后对比各册字符数增量，非预期变动即回滚
  （本次 S20 正则吞括号 bug 正是由 KaTeX 质量门 + 字符数核对检出的）。

## 4. 产品形态：核心独立、适配层可插拔（先解耦，再封装）

### 4.0 核心原则：先有可移植核心，再有入口

**真正值钱的是 2863 行引擎，不是某个平台的"技能"。** 因此产品化的第一约束是：
核心包（`book2md`，纯 Python + Node/KaTeX）必须**零平台绑定**，可 `pip install` 后在
任何环境（CI、其他 IDE、其他 Agent 框架、裸服务器）独立运行。WorkBuddy 技能包、CLI、
未来的 Web UI 都只是**薄适配层**，调用同一个核心，谁都能换。

### 4.1 平台解耦审计（已用 grep 实证，非口头保证）

对现有 `gzsx-md/` 8 个核心脚本扫描结论：

| 检查项 | 结果 | 性质 |
|---|---|---|
| WorkBuddy SDK / API 硬引用 | **无** | 引擎不 import 任何 workbuddy 模块 |
| 外部网络/API 调用 | **无**（仅 `run_blocks.py` 命中内网 `<网关地址>:8000`，但该文件不在核心 8 文件内，属可选辅助） | 核心离线可跑 |
| 第三方 Python 依赖 | **无** | 仅标准库：os/re/sys/io/json/html/subprocess/glob + `html.parser` |
| 运行时外部组件 | 仅 **Node.js + KaTeX**（经 `subprocess` 调用），KaTeX 是通用 JS 库 | 标准、可换 |

**存在的 3 处"隐式耦合点"（均非逻辑绑定，一行可解）：**
1. `postprocess.py` / `rematch_merge.py` / `run_blocks.py` 中 `ROOT = r"C:\Users\xiesh\WorkBuddy\..."`
   只是硬编码的项目绝对路径——参数化即可，与 WorkBuddy 无关（任何工具都得配路径）。
2. `run_pipeline.sh` 用 `.workbuddy/binaries/python/...` 作解释器——只是"用哪个 python"，
   换成任意 Python 3.13 即可。
3. `scan_md_preview.py` 文档串提到"WorkBuddy 预览"——纯注释，删字即可。

**结论：引擎本身已通用；唯一会"绑死"WorkBuddy 的风险，是把技能包当主交付物并把逻辑写进
SKILL.md。规避=逻辑全留核心包，技能壳逻辑零嵌入（结构见 §4.2.3）。**

### 4.2 产品交付形态：一核一壳（2026-10-24 深化重写）

#### 4.2.0 产品定义（先说清"产品是什么"）

**产品 = 一个独立的教材 PDF 转换工具（核心包）+ 一个可选的 WorkBuddy 技能壳。**

```
输入：课本 PDF（如 化学必修第一册.pdf）
输出：markdown.md + images/ + 阅读版 HTML + 知识库版 HTML + TOC + 质检报告
依赖：Python 3.13 + Node.js + 可访问的 MinerU 网关（可插拔后端，见 §4.3）
约束：不依赖 WorkBuddy——CI、裸服务器、其他 Agent 框架均可运行
```

三个易混概念的对齐（此前讨论中暴露过混淆，此处钉准）：

| 概念 | 是什么 | 类比 |
|---|---|---|
| **产物** | 每本书转换得到的 HTML / md+图片+公式 / 质检报告 | 工厂出的货 |
| **产品** | 核心包（引擎+配置+CLI）+ 技能壳 | 工厂 + 对话前台 |
| **规则数据** | `packs/`（学科规则包）与 `overlays/`（书目裁定规则） | 老师傅经验写成的工艺卡 |

#### 4.2.1 交付形态：一个版本化仓库，"工厂 / 车间"两棵树分离

产品以**一个内部 git 仓库（或 zip 发行包）交付**，带版本号。仓库（工厂）与运行数据（车间）严格分离：

```
【工厂：产品仓库，装一次，带版本管理】
book2md/                        ← 仓库名（C 方案，见 §4.2.6）
├── book2md/                           ① 核心包（必选，pip 可装）
│   ├── 引擎：修复/渲染/探测器/质量门流水线（现有 ~3800 行参数化重组）
│   ├── 资产：katex/ 字体 + render_formulas.js（随包分发）
│   ├── 内置配置：configs/backends/ + configs/<科目>.json
│   ├── packs/<学科>/                 ← L1 学科规则包（产品自带，随版本演进）
│   └── baselines/                    ← 基准样本初始集 + 基线指标（防后端漂移）
├── skill-book2md/              ② 技能壳（可选，依赖①；前缀仅仓库内区分用）
│   ├── SKILL.md                      ← ~50 行编排手册（触发条件 + 流程编排）
│   ├── scripts/                      ← precheck / adjudicate_sheet / overlay_scaffold / verify_delivery
│   ├── references/                   ← process / ocr-patterns / backend-contract / troubleshoot
│   └── assets/                       ← 报告模板
└── docs/                             ③ 三份手册
    ├── install.md                    ← 装 Python+Node → pip install → 拷技能目录，共 3 步
    ├── onboarding.md                 ← 新书接入指南
    └── backend.md                    ← MinerU 网关契约：地址、版本锁定、补丁状态、指纹登记

【车间：工作区 workspace，用户数据，每科目/每项目一套】
D:/教材工作区/                        ← 位置由分层配置决定（见 4.2.4）
├── out/<书名>/                       ← 产物堆放区（md/images/HTML/质检报告/issues.json）
├── overlays/<书名>/                  ← C 档裁定沉淀的规则（用户数据，不进产品仓库）
├── blocks/<书名>/                    ← MinerU 分块缓存（断点续跑）
├── ledger.json                       ← 抽取账本 + 版本指纹
└── baselines-local/                  ← 本地回归比对结果
```

**归属原则**：产品仓库只放"引擎 + 自带规则 + 手册 + 基准样本初始集"；
工作区放一切"用出来的"数据（产物、裁定规则、缓存、账本）。产品升级不会搅动用户沉淀。

#### 4.2.2 为什么"只有一个 skill"不够（压力测试结论）

skill 目录理论上可以装下一切（引擎、资产全塞 `scripts/` 也能跑），但推演四个真实场景全部失效：

| 场景 | 只有 skill 会怎样 |
|---|---|
| **CI / 定时批量**（假期把 6 本化学书排成任务过夜跑） | skill 只存在于 WorkBuddy 会话里，CI 调不到，无人值守无入口 |
| **换一台机器**（同事电脑、新服务器） | skill 随 WorkBuddy 配置走，那台机器没有这个产品 |
| **版本管理**（规则迭代 20 轮后，哪版修的哪本书？） | skill 是"拷文件夹"式分发，无版本号、无变更记录、无回滚 |
| **测试纪律**（改一条正则，如何保证五册不回归？） | 引擎需要单元测试 + 逐册回归 + 字符数核对，这些工程实践长在包上，不长在技能目录上 |

**结论：核心包是产品本体（每一行场景表它都在），技能壳是第一个"应用"（只在对话场景那一行）。
把引擎塞进 skill = 把工厂装进遥控器，正是 §4.0/Q1 纪律要防的死法。**

#### 4.2.3 技能壳的完整设计：结构、调用机制、纪律边界

**调用机制（三层接力）**——skill 本身不执行任何东西，它是一份说明书，让助手用现成的
Shell 工具调 book2md 命令：

```
你说"转化学必修一"
  → ① WorkBuddy 加载 SKILL.md（纯文本注入上下文）
  → ② 助手按手册用 Bash/PowerShell 工具执行：b2m run --subject chem-renjiao --book 化学必修第一册
  → ③ book2md 进程干活，结果写入工作区文件
  → ④ 助手读结果 → 汇报 → present_files 呈交交付物
```

**内容归属分工**（skill 三类资源的职责边界）：

| 内容 | 去处 | 理由 |
|---|---|---|
| 转换/修复/渲染逻辑 | book2md 核心（永远） | 平台无关、可测试、可版本化 |
| 编排 glue、环境预检、报告核验 | skill `scripts/` | 确定性多步操作封装成脚本，防助手临场发挥漏步 |
| 方法论知识、处置手册 | skill `references/` | 按需加载：触发时只载 SKILL.md，质量门失败才读 troubleshoot.md，节省上下文 |
| **严禁** | 把修复正则、转换逻辑写进 SKILL.md 或 skill 脚本 | 逻辑嵌入 = 平台绑死 |

**分工实例**：跑修复、渲染、质量门由 book2md 做（确定性代码，快且稳）；
C 档存疑内容复核由对话助手做（联网查教材官网、目检 PDF、多源交叉验证、与用户确认——
这恰是对话式 AI 的强项）。CLI 干粗活，对话干判断。

**为什么暂不做 MCP**：book2md 是单机工具、命令即接口，Shell 调用最简单可靠。
将来若要让团队多客户端共享转换服务，再包一层 MCP server，核心零改动。

#### 4.2.4 工作区与路径配置（分层解析，单一事实源）

**引入 workspace 概念**：`out/` 的位置不是孤立配置，而是工作区的一部分
（含产物、overlays、blocks 缓存、账本，见 4.2.1 车间树）。

book2md 解析工作区路径按固定优先级（高 → 低）：

| 优先级 | 来源 | 用途 |
|---|---|---|
| 1 | 命令行参数 `--workspace D:/教材工作区` | 单次运行临时指定 |
| 2 | 环境变量 `B2M_WORKSPACE` | CI/定时任务一次设定 |
| 3 | 用户配置文件 `~/.book2md/config.json` | 个人默认值，写一次永久生效 |
| 4 | 默认值 `./out`（当前目录） | 零配置开箱即用 |

`~/.book2md/config.json` 示例：

```json
{
  "workspace": "D:/教材工作区",
  "backend": "mineru-remote",
  "subjects": ["math-renjiao-a", "chem-renjiao"]
}
```

**skill 不需要自己的路径配置（单一事实源原则）**：book2md 每个命令的 stdout 输出
机器可读 JSON，携带全部已解析路径：

```json
{
  "workspace": "D:/教材工作区",
  "book": "化学必修第一册",
  "out_dir": "D:/教材工作区/out/化学必修第一册",
  "issues_file": "D:/教材工作区/out/化学必修第一册/issues.json",
  "exit_code": 0
}
```

skill 脚本只解析该 JSON、只转调 book2md——路径在 book2md 解析一次，CLI 与 skill 全部自动跟随，
换机器只改 `~/.book2md/config.json` 一处。

**Windows 实现约束**：工作区路径含中文是常态，配置层统一 UTF-8 + `pathlib.Path`
处理（本项目教训：中文文件名曾在 `ls` 与批处理中乱码）。

### 4.3 抽取后端：远程 MinerU 服务的适配层设计（Q3 深化）

#### 4.3.0 先澄清"外部 API"的两种含义（决定风险等级）

你仓库里的 `run_blocks.py` 已给出真实形态——它直连 `http://<网关地址>:8000`
（RFC1918 私网地址），按 40 页一块提交、下载 zip、重映射页码、用 `ledger.json`
断点续跑，并实现了 403 限流退避（0/30/90s）。也就是说：

- **形态一（你正在用的）：内部自托管网关**。API 跑在你们自己的内网服务器上。
  **数据不出组织、无按页计费、可用性/版本你可控**——这是"外部 API"里
  **风险最低、最值得保留**的一种。
- **形态二：公共第三方 SaaS**（官方 MinerU 云 API / Mathpix 等）。零基础设施，
  但教材 PDF（受版权保护）会离境、按量计费、供应商锁死、模型升级不可见。

**结论：把抽取当"远程服务"是合理架构，但前提是做成"适配层"，而非把
`curl <网关地址>` 写死进核心。** 两种形态都能接，推荐默认用形态一。

#### 4.3.1 为什么"抽取 = 远程服务"这个方向本身是对的

1. **抽取是整条链路里最重、最易变的一段**。MinerU 要 GPU、要下几个 G 的模型、
   OCR 引擎质量随版本漂移。把它当作"服务边界"隔离，正好契合 §2/§3 的设计——
   真正值钱、可控、可复用的资产全在阶段 B（修复+渲染+质检，2863 行），阶段 A
   只需一个干净的"PDF 进 / md+图 出"接口。
2. **与 Q1 同构的纪律**。Q1 我们决定"核心独立于 WorkBuddy、用适配层转调"；
   MinerU 也应如此：核心永不 import 网关地址，只依赖 `PdfExtractor` 接口。
   这样对称、一致，也避开了"换一个外部依赖就改核心"的陷阱。
3. **你已有生产级编排可迁移**。`run_blocks.py` 的块切分、zip 解包、页码重映射、
   ledger 续跑、限流退避——都是成熟的远程抽取编排，应整体迁入
   `RemoteMinerUAdapter`，而不是丢掉重写。

#### 4.3.2 适配层设计（核心不碰网关，只认接口）

```
engine/extract.py            # PdfExtractor 抽象接口（核心只认这个）
  ├── RemoteMinerUAdapter    # 迁 run_blocks.py 逻辑：块提交 / zip / 页码重映射 / ledger / 退避
  │     endpoint、tier、page_range、response_format 全参数化（不再硬编码 IP）
  ├── LocalMinerUAdapter     # 可选：subprocess 调本地 mineru（离线/内网不可用时的回退，fallback）
  └── PublicApiAdapter       # 可选/未来：公共 SaaS（仅对外分发时用，默认不启用）
```

契约要点（把 `run_blocks.py` 当前的**隐式约定**显式化）：
- 输入：PDF 路径 + `page_range`；输出：`markdown.md` + `images/` + `middle_json.json`。
- 解包布局：根直接是 `markdown.md` 或 `0001/` 子目录（两种都兼容，现有代码已处理）。
- **版本指纹（build provenance，服务版本与配置的溯源元数据）**：每次抽取把后端 version/tier/模型标识写入 ledger——这是远程依赖
  最关键的防腐手段（见下）。
- **契约测试（contract testing）**：对 zip 输出格式做 schema 断言，网关改版第一时间报错而非静默错乱。

#### 4.3.3 远程抽取的三大风险与对策（这是"适不适合"的真正答案）

| 风险 | 说明 | 对策 |
|---|---|---|
| **可用性** | 网关宕机 → 阶段 A 全停。这是远程依赖最大单点。 | 核心只认接口；网关挂 → 切 `LocalMinerUAdapter` 或备用端点，一行配置，核心零改。 |
| **版本/质量漂移** | 网关升级 MinerU 模型，OCR 输出变化，下游 S1–S20 规则（如 `\mathcal` 误识、`overline` 括号模式）可能静默劣化；且远程你更难察觉何时变了。 | **版本指纹 + 基准样本回归**：每次抽取记录指纹；怀疑变更后对固定基准样本重跑 QA 探测器矩阵，差异超阈值即告警。 |
| **输出契约脆弱** | zip 布局、`middle_json` 页码映射、`page_K_` 命名都是与网关的隐式约定，网关改版即崩。 | 把约定上升为版本化适配器 + 契约测试（见 4.3.2）。 |

**"PDF 是唯一事实源"原则不受损**：PDF 与 ledger 始终保存在本地，md 只是
**可再生的派生产物**。网关的 md 绝不视为权威；一旦网关不可复现，重跑 API 即得
（或切本地）。

#### 4.3.4 结论（已确认）

- **方向正确**：抽取以远程服务形态交付，既符合你现行做法，也契合"核心独立 +
  适配层可插拔"的全局纪律。
- **关键约束**：核心只依赖 `PdfExtractor` 接口；默认后端 = 你的内网网关（形态一）；
  公共 SaaS（形态二）仅在对外部署时启用，且需评估版权离境与成本。
- **用户已确认（2026-10-23）**：
  1. `<网关地址>:8000` 为**你们自托管网关（形态一）**——数据不出组织、版本与可用性自控。
  2. 默认后端即用此内网网关；一并实现 `LocalMinerUAdapter` 作宕机回退（§4.3.2）。
  3. 接受"版本指纹 + 基准样本回归 + 契约测试"作为远程依赖防腐机制（QA 成本已计入 P1）。
- **延伸确认的两项硬需求（已写入方案）**：
  - **版本锁定 + GPU 能力契约** → 见 §4.3.6（自托管形态一专属纪律）。
  - **OCR 工具无关性设计** → 见 §4.4（Canonical Extraction 契约 + 适配器矩阵）。

#### 4.3.5 现状对照：版本指纹 / 基准回归的落地状态（2026-10-23 核查）

- **版本指纹：未做**。`ledger.json` 仅记录每块的 `pending/done/failed` 状态
  （`books[].blocks` 值为字符串），不含任何后端 version/tier/模型标识。若网关未来
  静默升级，我们无从得知"今天的 md 是哪版 MinerU 产的"。
- **基准样本回归：未做**（作为纪律）。QA 工具链已具备——`scan3` D1–D10、`scan_render`、
  `scan_md_preview`、六道质量门自检都能跑；但**没有固定基准样本集 + 基线对比**这一环。
  全仓无 golden/sample 目录；`fix_md.py` 里的"回归方程"等是教材原文，与回归测试无关。
- **我们现有的近似机制**：① 六道质量门自检（保证当前输出自洽，能检测*灾难性*漂移，如
  KaTeX 错误数激增至千级）；② 字符数核对（S20 吞括号 bug 即由它 + KaTeX 质量门检出）。
  二者都是*内容级*弱代理，无法可靠捕获*细微*漂移（新型 OCR 错识模式会表现为新增 C 档，
  而非报错）。
- **含义**：§4.3.3 的对策是**新增工作**，非免费。P1 工作量应含：版本指纹写入 ledger（新增字段）
  \+ 基准样本集建设 + 基线比对脚本。

#### 4.3.6 后端版本锁定（version pinning）与硬件能力规格（自托管形态一的额外纪律）

确认 `<网关地址>:8000` 为**你们自托管网关（形态一）**后，版本与硬件的控制权在**我们手里**，
这恰恰是把"版本锁定"从愿望变成可执行契约的前提。本节把它写成可落地的规格。

**(a) 需要锁定的版本维度（三层，由外到内）**

| 层 | 钉什么 | 为什么必须钉 | 谁负责 |
|---|---|---|---|
| 网关封装版本 | 网关服务自身版本（它暴露 `/v1/file_parse` 的 wrapper）。若网关不报版本，需给它加 `/version` 端点或响应头 | 这是 API 契约（参数名、`tier`/`page_range`/`response_format`、zip 布局）的真实来源；换 wrapper = 换契约 | 网关运维 |
| 底层 MinerU 版本 | `mineru` 包版本（如 `mineru==1.x`） | S1–S20 规则是为"这版 OCR 的错误特征"调的；换版 = 错误模式可能整体变 | 网关运维 |
| 模型权重版本 | layout / OCR(PP-OCRv4) / 公式(UniMERNet) / 表格 各模型的具体 commit/哈希 | 同一 mineru 版也可能换权重；权重漂移同样改变输出特征 | 网关运维 |

> 注：从 `run_blocks.py` 看，`/v1/file_parse`、`tier`、`wait_timeout`、`page_range` 等参数
> **更像是这个网关自己的封装**，未必是 MinerU 官方 API 字段。因此"网关封装版本"才是我们
> 真正依赖的契约层；底层 mineru/模型版本作为版本指纹的附证。适配层（§4.3.2）负责吸收两层差异。

**(b) `tier` 必须锁定**
`run_blocks.py` 用的是 `tier=basic`。**OCR 质量档位直接决定下游规则的适用前提**——
`tier` 一变，我们调出来的 `\mathcal` 误识模式、`overline` 括号模式可能整体失效。
契约要求：book2md 调用时显式传 `tier`，且 ledger 记录实际生效的 `tier`。

**(c) GPU 能力规格（自托管 box 必须满足，供运维核对）**
MinerU 推理栈对 GPU 有硬性要求（数值为经验下限，非官方精确值）：

- **算力**：CUDA compute capability ≥ 7.0（Volta 代起）。
- **显存**：`basic` 档下 layout + OCR + 公式识别并发约需 **6–8 GB** 起步；
  并发多块解析或上 `high` 档，建议 **16 GB+**。
- **软件栈**：CUDA 11.8 / 12.x 驱动兼容；模型权重首次需联网拉取，之后本地缓存可离线。
- <网关地址> 这台机器的**实际 GPU 型号 / 显存 / 驱动版本需由运维核实登记**，写进后端契约文件（见下）。

**(d) 形式化载体：后端契约文件 + ledger 结构扩展**
- 新增 `configs/backends/mineru-remote.json`，记录上述全部锁定值 + 网关地址 +
  健康探测方式（`/health` 或 TCP 探活）。book2md 启动时校验"实际版本指纹 ∈ 契约允许集合"，
  不符即告警（而非静默接受）。
- `ledger.json` 增 `backend` 字段：`{kind, gateway_version, mineru_version, model_hashes, tier, gpu_spec, ts}`，
  落实 §4.3.3 的版本指纹写入要求。
- **自托管意味着 SLA 由我方自行保障**：① 任何升级先过基准样本回归（§4.3.3 / §4.4.5）；
  ② 旧版 md 因版本指纹可追溯、可重跑；③ 网关不可用时切 `LocalMinerUAdapter`（§4.3.2）。

**(e) 服务端源码补丁必须纳入版本指纹（本项目实测教训，2026-10-23 复核发现）**
网关机上 MinerU 的 `model/ocr/image.py` 已被 AST 级源码补丁修改
（`img_crop_width/height` → `int(max(1.0, round(...)))`，防 0/负裁剪；
见 `patch3/4/5_mineru_image.py`，幂等、带 ALREADY-PATCHED 检测、同版本重装后可重新应用）。含义：

- **版本指纹必须含补丁状态**：`backend.patched_files: [{path, patch_id, hash}]`。
  否则 pip 重装/升级 mineru 会**静默冲掉补丁**——图片裁剪行为改变而无人察觉，
  这正是"同一版本 ≠ 同一后端"的实例：版本 + 补丁状态合起来才算同一版本指纹。
- 补丁脚本产品化：纳入网关运维手册与契约测试（book2md 启动/抽取前校验补丁在场，
  缺失即告警）。

#### 4.4 OCR 工具无关的抽取抽象层（Canonical Extraction 契约）

**用户关键提问**：若将来不是 MinerU 做 OCR，管线会怎样？在"OCR 工具"与"最终
MD+图片+middle_json"之间，如何提高兼容性？本节给出设计。

##### 4.4.0 关键认知：当前"MD+图片+middle_json"其实是 MinerU 私有的

`middle_json` 是 MinerU 的中间格式——`pages[].page_idx` 与 `blocks[].type=="page_number"`
是我们页码重映射的根基。换句话说，阶段 B 今天**直接吃了 MinerU 的私有格式**。
一旦换工具，这份私有契约就断了。

**正确做法**：在 OCR 工具与阶段 B 之间插入一层**工具无关的标准化契约**
（Canonical Extraction），让阶段 B 永远只认这层契约，永远不碰任何工具的私有输出。
`middle_json` 降级为"MinerU 适配器内部的临时中介"，不再是阶段 B 的输入契约。

##### 4.4.1 架构：适配器在中间，契约在核心

```
   OCR 工具（任一）                适配器（每个工具一个）              阶段 B 引擎
 ┌───────────────┐              ┌──────────────────────┐         ┌──────────────────┐
 │ MinerU 远程    │              │ MinerUAdapter        │         │ fix_md (S1–S20)  │
 │ Mathpix API    │──原生输出──▶ │ MathpixAdapter       │──契约──▶│ KaTeX 预渲染     │
 │ Marker 本地    │              │ MarkerAdapter        │         │ 双版本 HTML      │
 │ 本地 VLM       │              │ VlmOcrAdapter        │         │ 六道质量门质检         │
 │ 人工 md        │              │ ManualAdapter        │         │ （只认契约）     │
 └───────────────┘              └──────────────────────┘         └──────────────────┘
        每种工具的私有格式/zip布局/页码信号         ↑ 全部吸收在这里           ↑ 与工具完全解耦
```

阶段 B 不 import 任何 OCR 工具；换工具 = 写一个适配器 + 过一遍基准回归，**S1–S20 一行不改**。

##### 4.4.2 Canonical Extraction 契约（阶段 B 唯一输入规格）

定义一份冻结的 JSON 契约（阶段 B 只依赖它）：

```jsonc
{
  "schema": "book2md.extraction/v1",
  "source_pdf": "必修第一册.pdf",
  "meta": {                        // 版本指纹（源自 §4.3.3）
    "tool": "mineru-remote",       // 适配器名
    "tool_version": "gateway-2.3 / mineru-1.2.1 / models:abc123",
    "tier": "basic",
    "extracted_at": "2026-10-23T19:00:00+08:00"
  },
  "pages": [                       // 物理页序列（页码映射的唯一真相源）
    { "physical_page": 1, "extraction_index": 0, "image_refs": ["page_1_001.jpg"] },
    { "physical_page": 2, "extraction_index": 1, "image_refs": ["page_2_001.jpg"] }
    // extraction_index 允许为空（VLM/人工场景靠 <!-- page:N --> 标记重建）
  ],
  "images": [                      // 图片清单（替代零散 page_K_ 命名）
    { "asset": "images/page_1_001.jpg", "physical_page": 1,
      "bbox": [x,y,w,h], "alt_source": "caption|auto|author" }
  ],
  "markdown": "必修第一册.md",      // 规范化 md：数学用 $...$/$$...$$，
                                    // 图引用用 ![alt](images/page_1_001.jpg)
  "blocks": null                   // 可选：原生布局块（MinerU/Marker 有；VLM/人工可为 null）
}
```

**契约要点**：
- **数学方言冻结**：`$...$` 行内、`$$...$$` 块——这正是 fix_md S1–S9 已假设的 texmath 方言，
  适配器负责把各工具输出 coerce 成它，阶段 B 零改动。
- **图片用清单 + 规范命名**替代"约定俗成"的 `page_K_`，且每个图带 `physical_page` 与 `alt_source`，
  杜绝"图片失联 / 页码错位"两类老问题。
- **`pages` 数组是页码映射的唯一真相源**：彻底取代"靠 middle_json 解析推导"，任何工具都能填它。
- **页序归一化属于适配器职责**：分块提交的产出按"完成顺序"到达（本项目实测曾出现
  87–126 页排在 47–86 页之前），适配器必须按物理页序重排后才可填入 `pages[]`
  （rematch_merge.py 的既有逻辑迁入各适配器）。
- **`meta` 即版本指纹**：一次抽取生成一份指纹，写入 ledger（§4.3.6）。

##### 4.4.3 适配器矩阵：未来非 MinerU 管线的具体形态

下表说明"换工具时实际要写什么、吸收什么差异"——这就是兼容性设计落地的全貌：

| 候选 OCR | 原生输出 → 适配器要做的事 | 页码映射来源 | 质量 / 性质 | 适配成本 |
|---|---|---|---|---|
| **MinerU（当前）** | 解 zip、归一化 `page_K_` 命名、**块完成序→页序重排**（迁 rematch_merge.py）、迁移 middle_json | `pages[].page_idx` + `page_number` 块 | 自托管、可控 | 基线（已迁 run_blocks.py） |
| **Mathpix API** | 取 `markdown` 字段、base64 图解码写入、强制数学方言 | 元素级 `page` 字段 | 商业、数学极强、付费 SaaS（形态二·离境） | 低（本就输出 md） |
| **Marker**（开源） | 类似 MinerU：md + JSON(含页信息) + 图 | JSON 的 page 信息 | 开源、可自托管、Mathpix 平替 | 低（与 MinerU 同构） |
| **Nougat**（开源） | 直出 LaTeX/md、按页切分 | 模型按页输出 | 学术/STEM 强、数学友好 | 中 |
| **本地 VLM**（Qwen-VL/GLM-4V/GPT-4V） | 让模型输出方言 + `<!-- page:N -->` 标记；图裁剪另交工具 | 标记重建 | 回退手段、零 OCR 引擎依赖、质量波动 | 中（需精心 prompt + 后校验） |
| **PaddleOCR+PP-StructureV2+UniMERNet** | 组装 MinerU 同款组件 | 布局模型给出 | 完全自控管线 | 高（等于自建 MinerU） |
| **人工 md** | 取作者写的 md + 其放置的图；读其插入的页码标记 | 作者标记 | 事实源的最终回退手段、速度慢 | 极低（几乎透传） |

**结论**：换 MinerU 不构成架构风险——它只是适配器矩阵里的**一行**。阶段 B 资产（2863 行）
对任一工具通用；新工具 = 一个新适配器文件 + 一份基准回归基线。

##### 4.4.4 提高兼容性的五条具体纪律

1. **阶段 B 永不直接读私有格式**：任何 `middle_json` / Mathpix JSON / VLM 响应都**只在适配器内**
   解析，产物一律过契约。违反此条的代码一律不予通过评审。
2. **适配器版本化 + 契约测试**：每个适配器绑定其工具版本；给一个 canned 原生输出 fixture，
   断言适配器产出的 Canonical Extraction 通过 schema 校验（图数、`pages` 完整性、数学定界符存在）。
   工具改版 → 适配器版本升级 + 契约测试第一时间报错，而非静默错乱。
3. **版本指纹 + 基准回归校验正确性（非仅结构）**：§4.3.3 的基准样本回归验证的是**适配器产出的质量**
   （过全套 QA 探测器），不是只验 schema。这是检测"换工具/换模型后静默劣化"的最终手段。
4. **优雅降级**：无 `blocks` 的工具（VLM/人工）也能跑——`pages` 由标记重建，图片 `alt` 由
   作者/模型提供；阶段 B 对"无自动 alt"的情形提示人工补，而非崩溃。
5. **契约冻结、向后兼容**：契约版本升级走 `v1→v2` 且旧版适配器保留，阶段 B 按 `schema` 字段分派，
   不破坏存量工作区。

##### 4.4.5 实施成本与落地顺序

- **P1（与核心同步）**：定义契约 schema（§4.4.2）+ `ExtractorAdapter` 抽象 + `MinerUAdapter`
  （迁 run_blocks.py）+ 契约测试框架。**不写其他适配器**，但契约已为它们预留扩展位。
- **P2+（按需）**：首个非 MinerU 需求出现时，挑上表中最贴近的适配器实现（大概率 Marker 或
  Mathpix 作"质量基准"），用基准回归校准。届时阶段 B 零改动即为兼容性设计成立的证据。

### 5.1 与数学的共性与差异

| 维度 | 数学（已通） | 化学 | 物理 |
