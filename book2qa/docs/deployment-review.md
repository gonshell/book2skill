# deployment-review.md — 部署形态审查：哪些组件不能跑在学生设备上

> 触发：用户指出 172.20.4.209 只是开发/测试/试用地，**实际给学生用需要部署
> 排序算法 API**。本审查逐组件检查现有设计在"学生本地手机/电视/笔记本"上
> 的可行性，并给出生产形态的修正清单。
>
> 结论先行：**除"答案渲染"外，现有设计的全部组件都不适合学生设备本地运行**，
> 但不适合的原因分三类，处置各不相同。

---

## 1. 逐组件审查

| 组件 | 手机 | 电视 | 笔记本 | 不适合的原因（分类） | 生产形态归属 |
|---|---|---|---|---|---|
| `b2q build`（建库） | ✗ | ✗ | ✗ | **A 算力/环境**：解析 8 万字 md + 页锚定 + 抽取，学生永远不需要 | 运营侧离线跑，产出发布 |
| `b2q index`（向量索引） | ✗ | ✗ | ✗ | **A**：onnxruntime + 150MB 模型 + 全册编码 | 服务端，更新时跑 |
| R4 向量推理 | ✗ | ✗ | △ | **A**：150MB 模型 + 推理运行时，手机/电视无 Python | 服务端 API |
| R1/R2/R3 排序（RRF） | △ | ✗ | △ | **C 随数据走**：计算本身轻（纯文本），但索引与教材库在服务端 | **服务端 API（排序算法 API）** |
| 学生 store（掌握度/错题） | △ | ✗ | △ | **B 数据属性**：单机 sqlite 换设备即丢、无法跨端、家庭多孩场景失效 | 服务端存储 + **账号维度（设计缺口，见 §3）** |
| context（会话承接） | △ | ✗ | △ | **B**：跨设备续问需要服务端会话 | 服务端 |
| review 排程（SM-2/due） | △ | ✗ | △ | **C**：状态在服务端，due 随之 | 服务端 |
| 教材原文 + 图片（751 张，~200MB） | ✗ | ✗ | △ | **B 体积**：按需取，不预装 | 服务端按需返回（图片策略见 §3） |
| 图谱 graph.jsonl（46 行，几十 KB） | △ | △ | △ | **C**：小，但随 API 走一致性好 | 服务端（可缓存到端） |
| 答案渲染（KaTeX/字体/排版） | ✓ | ✓ | ✓ | **唯一适合本地的**：WorkBuddy/浏览器前端能力 | 学生设备 |
| 意图识别/输出模板选择 | — | — | — | 在 agent 运行时（WorkBuddy），本就不在学生应用层 | 不变 |

分类说明：**A = 算力/运行环境不可行**；**B = 数据体积/跨端/隐私属性决定**；
**C = 计算很轻，但为一致性与状态归属随服务端**。电视是特殊端：零输入，
只能做 learn/review 的**只读展示端**，ask/drill 需要输入的场景不可用。

## 2. 修正后的目标架构

```
学生设备（手机/电视/笔记本）＝ 纯前端
  WorkBuddy / App：对话 + 渲染（KaTeX 本地能力），零 book2qa 计算、零安装
        │ HTTPS + 账号 token
        ▼
b2q API 服务（自控服务器：学校内网 / 家庭 NAS / 云主机）
  ├─ POST /recall     排序算法 API（R1-R3 轻计算 + R4 向量推理）
  ├─ GET  /node/{id}  单节点全料
  ├─ GET  /section    learn 取节
  ├─ GET  /due        review 排程（SM-2 在服务端）
  ├─ POST /log        drill/ask 落 store（attempt/mastery/next_due）
  ├─ 教材只读库        graph / 原文 / 图片（按需）/ 向量索引
  └─ store            学生数据（账号维度，内网自控不出域）
        ▲
b2q build + index（运营侧离线跑，产物发布到服务端）
```

**保留不变的设计结论**：不用 Milvus/Qdrant（数据量小，numpy/内存索引够）；
不用第三方 LLM 云（skill 的 LLM 走 WorkBuddy 本体）；教材侧产物"只读可重建"。

**被修正的表述**：serving.md §1"纯本地运行时"整段——"纯本地"的真实诉求
（数据自主、无第三方依赖、无 API 费用）由**自托管**满足，不是客户端独立运行。

## 3. 由此暴露的设计缺口（需新增决策）

| # | 缺口 | 待决策 |
|---|---|---|
| 1 | **用户体系**：store 挂账号后，账号是什么？v1 最简 = 匿名设备码/邀请码（无手机号实名）；还是对接学校学籍？ | 用户定 |
| 2 | **部署位置**：真实学生从哪连？学校内网（学生同网）/ 家庭 NAS（仅自家）/ 公网云（需 HTTPS + 域名 + 备案考量） | 用户定 |
| 3 | **图片策略**：手机流量敏感——按需返回缩略图（生成缩略图进 build？）vs 原图 URL；内嵌 base64 禁用（流量 ×1.3） | 建议：服务端即时缩放 |
| 4 | **API 工程选型**：b2q serve 实现——标准库 http.server（零依赖但简陋）vs FastAPI（部署形态下合理，纪律改为"学生端零依赖"） | 建议 FastAPI |
| 5 | **会话/context 生命周期**：服务端保留多久、随账号还是随设备 | 建议：随账号，7 天过期 |
| 6 | **离线场景**：v1 明确不做（内网常态在线），文档写明边界 | 建议：v1 不做 |

## 4. 落地动作（确认 §3 决策后执行）

1. serving.md §1 部署章重写（三形态表：CLI 开发态 / 自托管试用态 / API 生产态）
2. skill-io 命令面补 HTTP API 契约（端点表 + 认证 + 错误码 + 流量预算）
3. `b2q serve` 新命令（API 壳，复用 retrieval 引擎不变）
4. store 模型加 account 维度（v1 字段：account_id 前置）
5. build 增加缩略图产出（若采纳图片策略）

## 5. 与现有评审批次的关系

BATCH-3 的读侧命令（section/due/log）直接按 **HTTP API 形态**设计，
CLI 形态降级为开发调试用——避免做出一套 CLI 再返工一遍 API。
